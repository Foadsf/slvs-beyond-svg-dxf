# 18 · Peaucellier: a straight line made of circles

Seven moving links and two fixed pivots turn circular input into straight
output. **There is no straight-line constraint on the output.** SolveSpace
finds it from the bar lengths. This is a native mechanism MWE, with an
optional 3D dressing driven by the same skeleton.

[![Open the interactive motion preview](out/preview.png)](out/motion.html)

**Start here:** open [out/motion.html](out/motion.html) locally and drag the
input-height slider. Every displayed joint position comes from one of 61
regenerated `.slvs` files. The browser plays those samples; it does not solve
the linkage or substitute an analytical animation. Link widths in this
planar preview are illustrative. GitHub's file viewer does not execute HTML.

## The one-line experiment

Open [linkage.slvs](linkage.slvs) and [linkage.height25.slvs](linkage.height25.slvs)
in SolveSpace. The files differ in exactly one value, on constraint `00000015`:

```diff
-Constraint.valA=-10
+Constraint.valA=-25
```

This is the signed distance of the **input** pin P from the horizontal
ground line OC. In this line orientation the negative distance gives
positive y. It selects a static pose of the rotating crank, rather than
adding a physical input slider.

| Input height P.y | Solved P.x | Solved Q.x | Solved Q.y |
|---:|---:|---:|---:|
| 10 mm | 68.541020 mm | 91.428571 mm | 13.339249 mm |
| 25 mm | 59.494897 mm | 91.428571 mm | 38.418661 mm |

The source contains rough initial guesses, 8 line requests (7 moving bars
plus construction ground), and 21 constraints. It contains no cached
entities, no output-coordinate dimension, and no output point-on-line rule.

## Why it works

The fixed pivots are O=(0,0) and C=(35,0). The long arms OA and OB are
L=100 mm; AP, PB, BQ and QA form a rhombus with side s=60 mm. The crank
CP has radius r=35 mm, equal to OC.

Let M be the intersection of the rhombus diagonals. On the distinct-joint
assembly branch, O, P, M and Q lie on one line. Subtracting the two
right-triangle identities gives

`OP * OQ = OM^2 - PM^2 = L^2 - s^2 = 6400 mm^2`.

Thus `Q = 6400 P / |P|^2`. The input circle is
`(P.x - r)^2 + P.y^2 = r^2`, so `|P|^2 = 2r P.x` and
**`Q.x = 6400 / (2r) = 91.428571428571... mm`**.

This is the classical [Peaucellier inversor](https://mathworld.wolfram.com/PeaucellierInversor.html).
The numeric check independently evaluates the circle's right-hand branch,
each bar length, the inversion product, collinearity and output position
from regenerated entities. It does not infer success from CLI exit status.

## Motion, with an actual failing control

`_build/sweep.py` walks P.y from -30 to +30 mm in 1 mm steps, using
continuation from the 10 mm pose. Each pose is written to a native file and
regenerated by SolveSpace. The output stroke is **103.449865888 mm**.

| Measurement | Nominal 35 mm crank | Deliberately wrong 36 mm crank |
|---|---:|---:|
| Regenerated poses | 61 | 61 |
| Maximum distance from expected output line | 5.68e-10 mm | 1.658523 mm |
| Output lateral drift (max x - min x) | below 1e-6 mm gate | 0.370796 mm |
| Straightness verdict | all accepted | all rejected |

Changing CP to 36 mm leaves a valid linkage and preserves the inversion
identity, but its input circle no longer passes through O. The output is
therefore curved. This control must solve successfully and fail specifically
on straightness; a parser error is not accepted as a successful control.

See [measurements.csv](out/measurements.csv) for all 122 rows and
[evidence.json](out/evidence.json) for the source hash and measured summary.
The 1e-6 mm positional gate is a numerical verification threshold, not a
claim of achievable mechanical precision. Area/product gates use 1e-4 mm².

**A real solver trap:** solving a remote pose from the same seed can fold
Q onto P. All seven bar lengths still pass. The invariant and output checks
reject that branch. Continuation keeps the intended configuration; the
offline check also constructs Q=P deliberately and requires rejection.
Large direct edits can likewise stall an individual capsule profile in the
3D version, so its second pose is reached by 1 mm continuation steps.

## Native solid version

![STL renders of both native solid configurations](out/solids.png)

- [Native assembly, input 10 mm](out/assembly.slvs) / [input 25 mm](out/assembly.height25.slvs)
- [STEP, input 10 mm](out/assembly.step) / [input 25 mm](out/assembly.height25.step)
- [STL, input 10 mm](out/assembly.stl) / [input 25 mm](out/assembly.height25.stl)

The auxiliary `_build/solid.py` composes native SolveSpace records. Each
link is a 10 mm wide capsule with two 5 mm through bores, extruded 2 mm.
Its arc centres are constrained to the skeleton's projected joint positions.
The arc/line joins use tangency; the bores follow the arc centres. Each
extrusion thickness is a driving distance to a generated top point, whose
handle is discovered from SolveSpace's own remap table.

OpenCascade independently reopens both STEP files and finds seven valid
solids each. All fourteen bores pass inside/outside probes at radii 2.49
and 2.51 mm on both sides. Per-link volume and thickness checks also pass.
The expected total volume is `9500 + 175*pi = 10049.778714 mm^3`.
The STEP volumes differ from it by less than 0.005 mm³ in either pose.
The per-link volume gate is 0.01 mm³, allowing STEP spline/export integration
error; it is independent of the deliberately perturbed initial guesses.

The existing `stl_inspect.py` checks every STL layer for closed edges and
consistent winding. Each has Euler characteristic -2, as expected for two
through bores. Removing a triangle must break watertightness, and probing
the solid web must reject the claim that it is a bore. The STL volume gate
is 0.2%, allowing tessellation at the specified 0.03 mm chord tolerance.
Full results: [solid-evidence.json](out/solid-evidence.json).

**Scope:** the links sit at z=0,3,...,18 mm in an exploded teaching
arrangement. Fixed-pivot supports, pins, spacers, bearings, tolerances,
friction, stiffness and swept interference are not designed. This is a
kinematic and parametric CAD demonstration, not a fabrication-ready machine.
The open skeleton is intentionally not an extrusion contour; SolveSpace's
raw sketch thumbnails show its open-contour warning. Use the motion page
for a clear kinematic view and the solid files for closed geometry.

## Reproduce

From the repository root, any platform with Python and `solvespace-cli`:

```text
python tools/build.py --cli PATH_TO_SOLVESPACE_CLI --only 18
python tools/check.py --only 18
python mwe/18_peaucellier/_build/sweep.py --cli PATH_TO_SOLVESPACE_CLI
python mwe/18_peaucellier/_build/solid.py --cli PATH_TO_SOLVESPACE_CLI
python -m unittest discover -s tests
```

The native models, sweep and motion page need only Python's standard
library and SolveSpace. The two auxiliary commands below run in a CAD
Python environment with `cadquery-ocp` for independent STEP verification
and `matplotlib` for rendering. Point `--stl-inspector` at the existing
[stl_inspect.py](https://github.com/Foadsf/dev-scripts/blob/main/stl_inspect.py)
tool; it is not copied into this repository.

```text
python mwe/18_peaucellier/_build/verify_solids.py --stl-inspector PATH_TO_STL_INSPECT_PY
python mwe/18_peaucellier/_build/render_solids.py --stl-inspector PATH_TO_STL_INSPECT_PY
```

For the presentation screenshot and browser interaction checks, with
Playwright and its Chromium browser installed:

```text
python mwe/18_peaucellier/_build/render_preview.py
```

`out/preview.png` is a browser screenshot of `motion.html`. `out/solids.png`
renders the actual STL facets with Matplotlib. The native CLI thumbnails
and SVG exports remain alongside them. Raw CLI logs stay local because
they contain absolute workstation paths. Generated native/STEP/STL files
follow the repository's existing ignore rules and must be built after cloning.
Run the commands in order: the shared build command clears old exports.

Tested with SolveSpace `3.2~8f4b12ca` on Windows, 2026-09-09. The CLI's
`version` command prints its version but returns 1 in this build
([entrycli.cpp, lines 186-188](https://github.com/solvespace/solvespace/blob/8f4b12ca/src/platform/entrycli.cpp#L186-L188));
the runner recognises that specific metadata response. Every regeneration
and geometry export must return zero.
